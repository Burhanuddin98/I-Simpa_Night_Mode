# Upstream I-Simpa's meshing pipeline for tutorial 1, reproduced (lens: pipeline)

Scratch folder: `B:/repos/I-Simpa_Night_Mode/target/investigate/pipeline/`. Nothing was deleted, no tracked files were touched, and cargo was not used. Scripts: `run_variants.py`, `tetgen_to_mbin.py`, `locate.py`, `run_spps.py`, `gabe_read.py`.

## Findings

**1. The 2019 tutorial mesh was made by TetGen 1.5, not 1.6, and I reproduced it byte for byte.**
- Every 2019 output file ends with the command that made it: `# Generated by meshing\tetgen\tetgen.exe -pq2 -A -n D:\picaut\AppData\Roaming\isimpa\current\instance1\temp\scene_mesh.poly` (`tail` of `proj_extract/instance2/temp/scene_mesh.1.*`).
- TetGen history in upstream (GitHub API, `commits?path=src/tetgen/tetgen.h`): `ef2f7648ce 2021-04-20 "Update tetgen to 1.6"`. Before that it was `4db335c123 2016-08-11 "Build tetgen from sources"`.
- The source just before the upgrade (parent `a0d4d43`) has header `// Version 1.5 // November 4, 2013`, and its CMake installs to `RUNTIME DESTINATION meshing/tetgen`. That is the same path as the 2019 trailer.
- I built that source with MSVC 2022 (`tetgen_pre16/tetgen15.exe`, sha `6f75c513aa3483c2`). With the tutorial's own `.poly` and `.var` and flags `-pq2 -A -n`, it gives 2,257 tets, 732 nodes and 934 floor faces, largest floor face 0.09975938290693406 m².
- Leaving out the `# Generated` line, all five outputs (`.node .ele .face .edge .neigh`) are byte-identical to the 2019 files. Preprocess on or off makes no difference.

**2. The tutorial's settings produce `-pq2 -A -n` plus a `.var`. They do not produce the new-project default `-pq5 -A -n -Y`.**
- The SPPS core's `mesh_conf` (`projet_config.xml:2479-2489`) and the TCR core's (`:2555-2565`) are identical: minratio=2, ismaxvol=0 (maxvol 100), isareaconstraint=1, constraintrecepteurss=0.1, appendparams="", userdefineparams="", preprocess=1, debugmode=0.
- Built through `projet_maillage.cpp:163-181` (`Convertor::ToString` uses precision 15, so 2.0 prints as "2"), that gives `tetgen.exe -pq2 -A -n  "<poly>"`. The 2019 trailer matches.
- `-pq5 -A -n -Y` is only what a new project starts with (`e_core_core_tetconf.h:100,103`). Turning on isareaconstraint clears `-Y` (`:85-86`).
- The `.var` holds `1 0 0.1` and `2 1 0.1`. It is written by `BuildVarConstraintFile` (`Objet3D_maillage.cpp:900-929`), which keys constraints by the facet's face index. The facet markers in the `.poly` are the same face indices.

**3. With the pinned TetGen 1.6.0 (sha `c1c754f1c6e06429`), the tutorial box gives 6 tets in every variant except the volume-constraint ones.**

| (b) no preprocess | 6 / 8 / 2 / 30.0 | 2257 / 732 / 934 / 0.0998 |

- Tutorial 1 has no `-a`: ismaxvol=0 on SPPS and TCR.
- The pinned TetGen does read the `.var`: stdout shows `Opening ...\scene_mesh.var.` (`runs/t1_a_gui_exact/tetgen.stdout.txt`). It then ignores it: (a) and (c2) both give 6 tets, and `-a0.1` gives 3314 tets with or without the `.var`.

**4. Why 1.6 ignores the `.var`: the area limit is stored but never tested.**
- In the vendored 1.6.0, `areabound` is set (`tetgen.cxx:13898-13906, 25066-25078`) and copied along, but no split test reads it. `check_subface` (`:27347-27388`) tests only the radius-edge ratio, and `checkconstraints` only controls storage (`:4761,4860,...`).
- In 1.5 (`a0d4d43`), `checkfac4split` does test it at `tetgen.cxx:24580-24586`: `if (checkconstraints && (areabound(*chkfac) > 0.0)) { if (area > areabound(*chkfac)) { qflag = 1; return 1; } }`.
- Upstream's vendored `tetgen.cxx` matches `libigl/tetgen` master (`4f3bfba399`, "V1.6") line for line once CRs are stripped (`diff | wc -l` = 0). So upstream vendored TetGen 1.6.0 without edits, and the 2021 upgrade silently dropped surface-receiver refinement.

**5. Preprocess leaves the tutorial `.poly` unchanged.**
- Before and after sha is `ab598bcab1548cfe` in every run.
- Its stdout: `Vertices merged : 0`, `Coplanar Faces destroyed : 0`, `Face splitted : 0`. No faces are split.
- The GUI calls it as `preprocess <path>` with the path unquoted (`projet_maillage.cpp:73-74`). `Preprocess.cpp:48-55` joins the arguments back together, so a path with spaces still works.

**6. How the GUI turns TetGen output into `tetramesh.mbin`, reproduced byte for byte.**
- `tetgen_to_mbin.py` applied to the 2019 `.1.*` files gives sha `8a6b3943dd47126b`, identical to the fixture (`cmp` passes, 234,492 bytes). Getting there needed two details that the Night Mode builder does not copy:
  - **Corner order is reversed.** Upstream writes each tet's corners as (d,c,b,a) and reverses the neighbour list. Without that, all 2257×25 integer fields differ; with it, all match. [inferred] The cause is argument evaluation order in `ivec4 sommets(ToInt(GetNextToken())-1, …)` (`Objet3D_maillage.cpp:161-164, 435-438`), which MSVC evaluates right to left.
  - **Coordinates go through a float32 round trip.** Upstream converts to GL coordinates and back, with UnitizeVar = (3, 1.5, -5, 0.2f) (`Objet3D.cpp:527-571`, `Mathlib.h:50-67`). Without the round trip, 198 of 732 nodes differ by up to 4.77e-7; with it, all 732 are bit-identical.
- Night Mode's builder keeps TetGen's order: "tetrahedra in `.ele` order, corners as written" (`crates/simpa-core/src/mesh/build.rs:118`).

**7. The 6-tet mesh does not crash SPPS when it is converted the way upstream's GUI does it. It crashes only with TetGen's own corner order.**
- The source (3, 5, 1.79999995) lies on the internal facet shared by tets 0 and 4. The float32 test in `locate.py` (a copy of `coreinitialisation.cpp:71-95`) gives these two numbers, with the normals built as `coreTypes.cpp:233` builds them:
  - Upstream order (`pinned_gui_exact_6tet.mbin`, sha `e456a8b400f18099`): the facet test gives −2.384e-7 in both tets, so the source counts as inside both and SPPS takes tet 0. spps.exe exits `0x00000000`, and "lost by meshing problems" is 0 in every band.
  - TetGen order, same nodes (`pinned_6tet_fileorder.mbin`, sha `8b4439c3ae3de8a5`): the test gives +2.384e-7 in both, so no tet contains the source. spps.exe exits `0xC0000005` in 0.0 s.
- The prediction matched the solver in both cases. The control (the 2019 mesh) exits `0x00000000`: the source sits in tet 435 with the closest facet 0.0946 away (0.0946 from the float test, before the 1/6 factor).
- So the crash comes from a sign flip of about 2.4e-7, not from the facet alone. Upstream's own conversion survives this case by that margin.
