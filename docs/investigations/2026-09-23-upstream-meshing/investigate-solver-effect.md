## Solver effect of the 6-tet mesh on tutorial 1 (upstream 1.4.0)

**Bottom line.** Remeshed with upstream 1.4.0's own binaries, tutorial 1 becomes 6 tetrahedra. With its own source at (3,5,1.8), SPPS crashes before writing any result. With the source moved 11 cm off that point, SPPS runs:
- the point-receiver results, total energy and T20 match the 2019 mesh to within 0.03 dB;
- the floor receiver shrinks from 934 faces to 2, so its 5.2 dB level gradient becomes a flat map.

The coarse mesh does no harm beyond the crash apart from wiping out the surface maps.

All scratch is in `B:/repos/I-Simpa_Night_Mode/target/investigate/solver-effect/`.

### Findings
1. **Which TetGen flags the tutorial uses.** Parsed `instance2/projet_config.xml` from `tutorial_1.proj` (sha256 `d778983d…`, appversion 1.3.4).
   - The `spps[SPPS]` core's `mesh_conf` is `minratio=2, appendparams="", isareaconstraint=1, constraintrecepteurss=0.1, ismaxvol=0, preprocess=1`. The GUI turns that into `tetgen.exe -pq2 -A -n <poly>` plus `scene_mesh.var`.
   - The 2019 `scene_mesh.1.*` files in the zip end with `# Generated by meshing\tetgen\tetgen.exe -pq2 -A -n …\scene_mesh.poly`.
   - A saved project is loaded through the XML constructor (`e_core_core_tetconf.h:45-53`), which never calls `InitProperties`. The `-Y` default and its toggle (`:82-103`) apply only to a new or user-edited `mesh_conf`.
   - The GUI remeshes on every run: `projet.cpp:751` calls `RunCoreMaillage`, and `projet_maillage.cpp:157` runs `ClearFolder`. So the committed 2019 mesh is never used by a 1.4.0 user.
2. **The TetGen version changed, and the problem was reported upstream in 2021.**
   - `v1.3.4/src/tetgen/tetgen.h` (raw.githubusercontent) says "Version 1.5, November 4, 2013". `929a5c8` `tetgen.cxx:7` says "Version 1.6.0".
   - PR #275, "Tetgen update" by wbinek, was merged into `dev` on 2021-04-20.
   - wbinek on 2021-04-23: *"Tetgen 1.6 does not respect the face area constrain properly. This leads to problems making maps on model surfaces… I would recommend reverting this update"*. No reply is recorded, and 1.6.0 is still at the tag.
   - Code receipt: `grep -n "[^t]areabound(" tetgen.cxx` finds only 3 hits outside the bound-copying `setareabound(…areabound(…))` lines (12361, 12606, 12726), and all 3 are commented out. The bound is stored (`:25075`) and never compared.
3. **Meshing with our pinned binaries and with the shipped 1.4.0 binaries gives the same 6 tetrahedra.**
   - Downloaded `isimpa-1.4.0_windows-no-install-x64.zip` (64,758,950 B, sha256 `b3670b26…`). It ships the identical `tutorial_1.proj`, `tetgen.exe` `a70854ac…` and `spps.exe` `9bc7db4c…`.
   - `preprocess.exe` changes nothing ("Vertices merged : 0 … Face splitted : 0"), and the `.poly` is byte-unchanged.
   - Every run printed `Mesh points: 8, Mesh tetrahedra: 6`, whether or not TetGen opened the `.var` ("Opening …scene_mesh.var."):
     - pinned `-pq5 -A -n -Y`, `-pq2 -A -n`+`.var`, `-pq5 -A -n`+`.var`
     - shipped `-pq5 -A -n -Y`, `-pq2 -A -n`+`.var`
   - The shipped `.1.node/.ele/.face/.neigh` equal the pinned ones, comment lines excluded. All five `.mbin` files are sha256 `8b4439c3…` (704 B).
4. **The `.mbin` builder is checked against upstream's own file.** `build_mbin.py` rebuilt the 2019 zip's `.1.*` outputs and compared them with the committed `tetramesh.mbin`.
   - All 2257 tets have the same face sets, markers and neighbours.
   - The rebuild differs only in the order of each tet's vertices: the 2019 file has (d,c,b,a). That is an even permutation, and both files have negative orientation on all 2257 tets.
   - 198 of 732 nodes differ by at most 4.8e-7 m.
   - [inferred] The 1.3.4 GUI wrote the corners reversed compared with `Objet3D_maillage.cpp:162-185` at 929a5c8.
5. **The crash.** Tutorial config, 6-tet mesh, source (3,5,1.8):
   - pinned `spps.exe`: 5/5 runs, seeds 1-5 at 10k particles, all exit `0xC0000005` in 0.0 s;
   - shipped `spps.exe`: seed 1 at 10k and the tutorial's own `random_seed=0` at 150k, both exit `0xC0000005`;
   - stdout is only `SPPS version 2.2.1`, stderr is 0 bytes, and no output files are written.
   - Barycentric test: (3,5,z) lies on a facet shared by two tets for z = 0.3, 1.0, 1.8, 2.5 and 2.9. The floor diagonal from (6,0) to (0,10) passes through (3,5). (3.05,5.1,1.8) is strictly inside tet 0.
6. **Outside the crash, results barely change.** Pinned `spps`, source (3.05,5.1,1.8), 10k particles, seeds 1-5, same seed on each mesh (`analyse_10k.txt`):

7. **What an upstream user sees, with the shipped binaries at the tutorial's settings** (150k particles, unseeded, source (3.05,5.1)):
   - 2019 mesh: floor Global level, averaged over area in 1 m bins of horizontal distance from the source, falls from -55.79 dB (under 1 m) to -61.02 dB (5 m and beyond). At 1 kHz it falls from -74.10 to -78.25 dB.
   - 6-tet mesh: the whole floor is two triangles, at -59.25 and -58.97 dB (0.27 dB apart).
   - Total floor energy agrees: -41.338 vs -41.327 dB.
   - Point levels are within 0.21 dB, which is inside the noise of a single unseeded run.
8. **TCR does not crash.** Shipped `classicalTheory.exe` on the 6-tet mesh at (3,5,1.8) exits 0.
   - `Main results.gabe` matches the 2019-mesh run to within 4.1e-7 relative, e.g. TR_Sabine 0.58057.
   - Its Direct, Sabine and Eyring surface maps also have 2 faces and 8 nodes, against 934 and 732.
9. **The GUI goes on as if nothing happened.** The `bool result = uiRunExe(...)` at `projet.cpp:811` is never read afterwards. The GUI still copies the parameters and refreshes the Results tab (`:819-835`). `processManager.cpp:172-176` logs "Program execution failed" only when `wxExecute` returns less than 0.

### What a 1.4.0 user running tutorial 1 gets
- **SPPS with the tutorial as shipped:** the tutorial's own flags (`-pq2 -A -n` with the 0.1 m² `.var`) give 6 tets, and the tutorial's source crashes SPPS. The report folder is left with no results. The GUI-default flags (`-pq5 -A -n -Y`) give the same mesh, so they cannot avoid the crash either (findings 3 and 5).
- **SPPS with the source moved off the x=3, y=5 line:** it runs. Point results and T20 are correct to within noise, but the surface receiver is a 2-face, flat floor map instead of 934 faces (findings 6 and 7).
- **TCR:** it runs, and also produces 2-face maps (finding 8).
