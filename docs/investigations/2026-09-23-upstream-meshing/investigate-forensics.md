## Forensics: upstream's 2019 tutorial-1 mesh (lens: mesh + project settings)

Scratch files are in `B:/repos/I-Simpa_Night_Mode/target/investigate/forensics-tut1/`. Nothing tracked was touched and nothing was deleted.

### Headline
The 2019 mesh came from **TetGen 1.5**, the source upstream vendored from 2016-08-11 to 2021-04-20. It was run with `-pq2 -A -n` and the `.var` area constraint (0.1 m² on markers 0 and 1), and TetGen 1.5 enforced that constraint. I rebuilt that TetGen 1.5 source and ran it on the 2019 `.poly` + `.var` with the same flags. The output bodies of `.node`, `.ele`, `.face`, `.edge` and `.neigh` are **byte-identical** to the 2019 files. Upstream moved to TetGen 1.6.0 on 2021-04-20, and 1.6.0 stores the area bound but never reads it. So "our" 6-tet mesh is upstream's own regression. It is not caused by our importer or by our flags.

So every 2019 tutorial mesh falls inside the TetGen 1.5 window.

### 2. Project settings (`instance2/projet_config.xml`, parsed as XML so each `mesh_conf` is tied to its core)

|---|---|---|---|---|---|

- In both, `userdefineparams=""` and `debugmode=0`.
- The report snapshots show the sequence. In the TCR run at 11h57m58s, TCR had area=1/0.1 while SPPS still had 0/5. By the SPPS run at 11h58m41s, SPPS had 1/0.1. Both runs wrote the same `tetramesh.mbin` (sha `8a6b3943dd47126b`, PROVENANCE.md).
- Minratio 2 with an empty `appendparams` was upstream's **default at the time**. Commit `bda1bb0e72` (2019-06-24, 17 days after this mesh) changed the defaults to minratio 5 and `-Y`, and added the rule that toggling the area constraint turns `-Y` on or off (API diff of `e_core_core_tetconf.h`). The belief that the default is `-pq5 -A -n -Y` is correct for projects made after that date, not for this one.
- **Our importer kept every setting that affects meshing.** `tutorial1_box.simpa:184-189` holds `min_radius_edge_ratio 2.0`, `max_volume_m3 null`, `surface_receiver_max_area_m2 0.1` and `preserve_boundary false`, which `tetgen_flags` turns into `-pq2 -A -n` + `.var`. That is exactly the 2019 command.
- Things the importer dropped:
  - `preprocess=1`, reduced to a note at `proj.rs:1559-1564`. Our `preprocess.exe` run on the 2019 `.poly` prints "Vertices merged : 0 / Coplanar Faces destroyed : 0 / Face splitted : 0" and leaves the file byte-identical, so it has no effect here.
  - The MD_Octave `-a0.1` setting. It was not used for this mesh: the trailer has no `-a`.
  - `debugmode`.
- Order of operations in the pre-1.6 GUI (`projet_maillage.cpp` @a0d4d43): `_SavePOLY` (:210), then preprocess on the `.poly` in place (:217; `Preprocess.cpp:103` saves back to the input path), then `.var` (:223), then tetgen (:237). So the zip `.poly` is the file TetGen actually read.

### 3. Analysis of the 2019 `tetramesh.mbin` (`analyse_mbin.py`, output in `mbin_analysis.txt`)
- 234,492 bytes = 8 + 12·732 + 100·2257: T=2257, N=732, every `idVolume` is 1, total volume 180.000000 m³ (6×10×3).
- Tet faces per marker (all hull faces, none on internal facets). The sums match the facet areas exactly:
  - 0: 465 faces, Σ 30.000 m², min / mean / max 0.0220 / 0.0645 / **0.0998**
  - 1: 469 faces, Σ 30.000 m², 0.0273 / 0.0640 / **0.0989**
  - 2–9 (walls): 16–71 faces each, max 0.85–1.98 m²
  - 10–11 (ceiling): 20 and 21 faces, max 3.40 and 2.33 m²
- **Only markers 0 and 1 (the z=0 floor, i.e. the surface receiver named in the `.var`) respect the ≤0.1 m² bound.** Everything else is coarse. The 1,270 hull faces match the `.face` header, and the per-marker counts are identical.
- Nodes: 513 of the 732 lie on the floor, 32 on the ceiling, and 95 are interior. Median edge length is 0.385 m on the floor and 1.833 m on the ceiling.
- Volumes: min 6.2e-4, median 2.3e-2, max **1.75 m³**. 379 tets exceed 0.1 m³ and 13 exceed 1 m³, so **no volume constraint was used** (`-a0.1` would cap every tet at 0.1). The mesh grades with height: for centroids at z<0.5 there are 1,514 tets with median 0.016 m³; at 2.5–3 m there are 51 tets with median 0.50 m³. That is what radius-edge (q2) propagation from a refined floor looks like.
- The `.ele` corner sets equal the `.mbin` corner sets row for row (sorted comparison True). The GUI only reorders corners within each tet.

### 4. Mechanism: reproduced, not inferred
I built `tetgen_2016/tetgen15.exe` with MSVC 2022 `/O2` from raw `src/tetgen/{tetgen.cxx,tetgen.h,predicates.cxx}` @4db335c123 (tetgen.cxx sha256 `c71ba56f…`, 1,097,747 bytes).

| binary | flags | .var | tets / nodes / faces / edges |
|---|---|---|---|
| TetGen 1.5 | `-pq2 -A -n` | yes | **2257 / 732 / 1270 / 212**, all 5 bodies byte-identical to 2019 |
| TetGen 1.5 | `-pq2 -A -n` | no | 60 / 31 / 58 / 40 |
| TetGen 1.5 | `-pq5 -A -n` | yes | 1362 / 585 |
| TetGen 1.5 | `-pq5 -A -n -Y` | yes | 18 / 11 |
| our 1.6.0 (`target/solvers/bin`) | `-pq2 -A -n` | yes or no | 6 / 8 / 12 / 18 (log shows "Opening scene_mesh.var.") |

- **Tutorial 3, TetGen 1.5:** all 5 files byte-identical.
- **Tutorial 2, TetGen 1.5:** ele/face/edge/neigh are identical. In `.node`, 1,036 lines differ only in the 17th printed digit (…312 vs …313). The parsed coordinates differ by exactly 0.0, so this is a difference in the C runtime's printf rounding.
- **Same flags, no `.var`, 1.6.0 against 2019:** tutorial 2 gives 123,718 tets (2019: 161,543) and tutorial 3 gives 2,137 (2019: 3,285). 1.6.0 also refines the boundary less when no constraint is involved.

Source receipts:
- TetGen 1.5 enforces the bound: `checkfac4split` (tetgen_2016 `tetgen.cxx:24535`, check at `:24580-24585`) marks the face for splitting when `checkconstraints && area > areabound(*chkfac)`. The bound is attached by facet marker at `:13451-13461` (`idx = in->facetmarkerlist[shmark - 1]`).
- 1.6.0 never enforces it: the vendored `tetgen.cxx` sets it at `:13898-13902` and `:25066-25075`, but every read of `areabound(` is commented out (`:12361, 12606, 12726`), and `check_subface` (`:27347-27388`) tests only `radius/emin > b->minratio`.
