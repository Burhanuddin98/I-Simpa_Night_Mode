# Bed for patch 0002, the sparse surface-receiver series (2026-10-06 15:51-16:04)

Design and mechanism: `SPARSE.md`. Scripts beside this file: `bed2_compare.py` (the comparison), `run_sampled.ps1`
(runs `spps.exe config.xml` in an arm's folder and samples its working set and commit every second), `density.py`
(the sparsity measurement that motivated the patch). Every arm's inputs are in `C:\tmp\nm-timebin-bed\<arm>\`.

Two solver builds from the pinned 929a5c8: **dense** = patch 0001 only (`spps.exe` code sha `143223ff…`, BED-0001's
arms B and C) and **sparse** = patches 0001 + 0002 (`spps.exe` code sha `d0ec3220…`, `solvers/manifest.json`).

## The seeded arms: the same input, bit for bit

Input: the 05:13 CR4-third `solve/` with `random_seed="12345"`, `nbparticules="20000"`, `nbparticules_rendu="0"`,
the first three bands (100, 125, 160 Hz), the Audience plane at 0.5 m (1,794 cells), 10 s at 1 ms. Every output
file compared: `.csbin` decoded through `simpa dump csbin`, the rest by sha256.

| Reference (dense) | Arm (sparse) | Files | Result | Peak working set, dense -> sparse | Time |
|---|---|---|---|---|---|
| B-new-step (bin unset) | sparse2-step (bin unset) | 39 | **IDENTICAL** | 237 MB (A-old, upstream's own build, same input) -> 52 MB | 27 s -> 27 s |
| C-new-10ms (bin 10 ms) | sparse2-10ms (bin 10 ms) | 39 | **IDENTICAL** | - -> 41 MB | 22 s -> 25 s |

The first sparse build (15:50) was not identical: the same 1,225,494 records in the 100 Hz file, none missing or
extra, 18,772 of them one float ulp apart (relative 6e-8; the record at face 0, step 424: 8.675919427e-10 against
8.675918872e-10). Cause, from the source: the particle's energy is `l_decimal` = `double` (`sppsTypes.h:72`) and the
cell a `float`, so upstream's `cell += energy` added in double and rounded once; the first `add(step, float)`
rounded the energy to float first. `add(step, double)` now does `cell = (float)((double)cell + energy)`; the
second build (15:58) is the one compared above.

## The production-size run the dense solver could not do

Input: the 05:13 CR4-third `solve/` with the Audience plane at **0.1 m** (43,930 cells), everything else as the
05:13 run: `random_seed="0"` (upstream's threads, 8 in flight), 18 bands, 300,000 particles a source, 2 sources,
10 s at 1 ms, `nbparticules_rendu="0"`.

| | Dense (upstream's allocation) | Sparse, realised |
|---|---|---|
| Sound maps in RAM | 43,930 x 10,000 x 18 x 4 B = **30.2 GB**, zero-filled at start-up; the machine's commit limit is 36.6 GB with the mesh, particles and point receivers on top; the 06:37 runs of this size aborted 15 s in | **3.07 GB** peak working set, 3.13 GB peak commit (270 samples a second apart) |
| Outcome | abort (0xC0000409, 06:17-06:38) | exit 0 in **273 s**, stderr empty |
| Map files written | - | 19 (18 bands + Global), 476,677,654 records, 3.67 GB on disk |
| 100 Hz map | - | 18,986,140 records (10.8 % of the 439 million cell-steps), 147 MB |
| Global map | - | 148,863,476 records, 1.14 GB |

The first sparse build's run of the same input (15:51): 275 s, 3.06 GB peak, 476,717,202 records; the second
build's record count differs by 40,000 because the run is unseeded (upstream's threads), not because of the fix.

Forecast against realised: 18 bands x 19 million cell-steps x 9 bytes = 3.1 GB; realised 3.07 GB. That is the
calibration `runSize.ts` carries (32 cell-steps a particle on CR4 over 10 s). The 275 s against the 05:13 run's 168 s
at 0.5 m is the fine plane's own cost (24 times more cells to intersect and write), with no dense run of it to
compare against.
