# TetGen outputs: `.node`, `.ele`, `.face`, `.neigh`

The tetrahedral mesh TetGen writes for a run, and the `_skipped.node` / `_skipped.face` pair it
writes instead when the input has intersecting facets. They are text files, read only here: we
run upstream's `tetgen.exe` and read what it wrote.

| | |
|---|---|
| Upstream loaders | `tetgenio::load_node` / `load_node_call`, `load_tet`, `load_face` in `tetgen/tetgen.cxx` (TetGen 1.6.0). **TetGen has no `.neigh` loader.** |
| Upstream writers | `tetgenmesh::outnodes` (`tetgen.cxx:33493`), `outelements` (`:33827`), `outfaces` (`:33979`), `outsubfaces` (`:34306`), `outneighbors` (`:34924`), `out_intersected_facets` (`:36038`) |
| Tokenizer | `tetgenio::readnumberline` (`tetgen.cxx:2894-2914`), `findnextnumber` (`:2926-2948`), then `strtol(.., 0)` / `strtod` |
| GUI consumers (reference only) | `LoadNodeFile`, `LoadEleFile`, `LoadFaceFile`, `LoadNeighFile`, `LoadFaceListeWithMarkers` in `isimpa/3dengine/Core/Objet3D_maillage.cpp:54-452`; the skipped pair in `isimpa/data_manager/projet_maillage.cpp:200, 248-274`, in the GUI's debug (`-d`) mode only |
| Rust | `crates/simpa-core/src/formats/tetgen.rs` |
| Oracle | `oracle/dump_tetgen.cpp`: `load_node`, `load_tet`, `load_face` unchanged; `.neigh` on TetGen's tokenizer |

Line numbers refer to `target/solvers/src-929a5c8/src/`. There is no `lib_interface` reader for
these files; TetGen's own loaders are the reference.

## Which files

I-Simpa's GUI writes `scene_mesh.poly` and runs `tetgen -pq<quality> -A -n [extra] scene_mesh.poly`
(`projet_maillage.cpp:163-181`). On success TetGen writes, with base name `scene_mesh.1`:

| file | writer | holds |
|---|---|---|
| `.node` | `outnodes` | the points |
| `.ele` | `outelements` | the tetrahedra; `-A` adds one attribute, the region number |
| `.face` | `outsubfaces` with `-p` | the boundary and internal facets' triangles, each with its `.poly` facet marker |
| `.neigh` | `outneighbors` (`-n`) | four neighbours per tetrahedron |

When the input facets intersect, TetGen stops and writes `scene_mesh_skipped.node` (every point at
that moment, through `outnodes`) and `scene_mesh_skipped.face` (the facets it skipped). Both come
from `out_intersected_facets`, which cuts the output name at its last `.`
(`tetgen.cxx:36042-36054`). Night Mode's fixture pair came from `model.poly` as `model_skipped.*`.
The skipped pair uses the ordinary `.node` and `.face` layouts.

A file's kind is its extension, never its bytes: an `.ele` without attributes and a `.neigh` can
hold identical text. Rust and the oracle both take the kind from the extension, ASCII case ignored
(Windows opens `X.NODE` as `X.node`).

## Text layer

This is how TetGen reads every one of these files. The Rust reader accepts a subset of it, marked
**Rust** below; see "The rule" further down.

- **Lines.** `fopen(.., "r")` (text mode, so `\r\n` becomes `\n`), then
  `fgets(buf, INPUTLINESIZE = 2048)` (`tetgen.h:70`, `tetgen.cxx:2900`). A line of more than
  2 047 bytes comes back in pieces, and each piece is read as a line of its own. A `Ctrl-Z` byte
  (0x1A) ends a text-mode read; a NUL byte ends the C string. **Rust:** lines are split at `\n`
  with one `\r` before it dropped. A line longer than `MAX_LINE = 2046` bytes, a NUL or a
  `Ctrl-Z` anywhere refuses the file.
- **Number lines.** `readnumberline` skips every byte that is not a digit, `.`, `+`, `-` or `#`.
  A line whose first such byte is `#`, or that has none, is skipped, and the next number line is
  the record. **Rust:** a line that is empty, blanks (space, tab) only, or blanks then `#` is
  skipped. Any other line is a record, and a record may not start with a comma.
- **Fields.** `findnextnumber` ends a field at a space, tab, comma, `#` or end of line, then skips
  anything that is not number-like. `#` ends the line. **Rust:** fields are separated by runs of
  space, tab and comma, and `#` starts a comment.
- **Integers** are read with `strtol(s, &end, 0)`: base 0, so `010` is octal 8 and `0x10` is 16.
  A C `long` is 32 bits on Windows, and overflow clamps. **Rust:** `[+-]?(0|[1-9][0-9]*)` in the
  `i32` range.
- **Reals** are read with `strtod`, into `REAL`, which is `double` (`tetgen.h:62`). **Rust:**
  `[+-]?(digits[.digits]|.digits)([eE][+-]?digits)?` with at most 768 significant digits and a
  finite value. No `inf`, `nan` or hexadecimal.
- **The trailing comment.** Every writer ends with `# Generated by <command line>`
  (`tetgen.cxx:33684, 33963, 34172, 34479, 34999`). `out_intersected_facets` writes none.

## Layouts

`[..]` is optional. `first` is 0 or 1: record numbers, and the point and tetrahedron numbers inside
records, count from it. TetGen writes `in->firstnumber` (the `.poly`'s first index), or 0 with
`-z`.

### `.node`: `load_node` (`tetgen.cxx:190-260`), `load_node_call` (`:69-182`)

```
<count> [<dim> [<attributes> [<markers> [<uv>]]]]        defaults 3, 0, 0, 0
<index> <x> <y> [<z>] <attr>*<attributes> [<marker>]      count lines
```

`outnodes` writes `%ld  3  %d  %d` and `%4d    %.17g  %.17g  %.17g`, then `  %.17g` for each
attribute and `    %d` for the marker (`:33535, 33599-33613`).

- `firstnumber` comes from the **first** point's index when it is 0 or 1. Otherwise it stays 0.
  Later indices are not read (`:108-115`).
- The count is parsed from the start of the line (`stringptr = inputline`, `:225-226`), not from
  its first number. A leading comma therefore makes the count 0 and shifts every header field one
  place.
- If `rbox` appears anywhere in the header line, the file is read as a qhull rbox file (`:221, 243-253`).
- A missing x, y or z fails the load (`:117-137`). A missing attribute becomes 0.0 (`:142-150`), and
  a missing marker becomes 0 (`:151-160`).
- With `dim` other than 3, z is not read and is set to 0.0 (`:128-137`).
- With `uv` nonzero, `pointparamlist` is allocated (`:96-101`) and never filled.

Exposed: `firstnumber`, `mesh_dim`, `numberofpointattributes`, `pointlist` (3 doubles per
point), `pointattributelist`, and `pointmarkerlist`, which is non-NULL whenever the marker flag is
nonzero, even for 0 points.

### `.ele`: `load_tet` (`tetgen.cxx:445-544`)

```
<count> [<corners> [<attributes>]]                         defaults 4, 0
<index> <corner>*<corners> <attr>*<attributes>              count lines
```

`outelements` writes `%ld  %d  %d` and `%5d   %5d %5d %5d %5d`, then `    %.17g` per attribute
(`:33868, 33915-33927`).

- `count <= 0` fails (`:470`). `corners` must be 4 or 10 (`:487`).
- The index is skipped, not read.
- A corner outside `[firstnumber, firstnumber + numberofpoints)` throws (`:521-526`). These are
  the `.node`'s values, so `load_tet` needs a loaded `.node`.
- A missing corner throws (`:516-520`). A missing attribute becomes 0.0 (`:530-538`).

Exposed: `numberoftetrahedra`, `numberofcorners`, `numberoftetrahedronattributes`,
`tetrahedronlist` (point numbers as written, base `first`) and `tetrahedronattributelist`.

### `.face` and `_skipped.face`: `load_face` (`tetgen.cxx:349-437`)

```
<count> [<markers>]                                         default 0
<index> <a> <b> <c> [<marker>]                              count lines
```

`outsubfaces` writes `%ld  %d` and `%5d   %4d  %4d  %4d`, then `    %d` (`:34349, 34442-34450`).
`out_intersected_facets` writes `%ld 1` and `%d  %d %d %d  %d` (`:36070, 36074-36078`).

- The count may be 0 or negative. Nothing is allocated unless it is above 0 (`:383-394`), so a
  negative count loads as success with no faces.
- Corners are checked like `.ele` corners (`:409`).
- The marker is read with `strtod` and cast to `int` (`:423-431`), so `2.7` reads as 2. A missing
  marker becomes 0.
- With `-o2` (`numberofcorners == 10`, set by an earlier `load_tet`), three extra corners are
  skipped (`:416-421`).
- `-nn` appends two adjacent-tetrahedron columns (`:34453`). The loader ignores them.

Exposed: `numberoftrifaces`, `trifacelist`, and `trifacemarkerlist`, which is non-NULL only
when the flag is nonzero **and** the count is above 0.

**The marker's meaning.**
- In a `.face`, it is the `.poly` facet marker (`shellmark`, `:34424`). I-Simpa sets it to the
  facet number, so it maps a triangle back to a scene face.
- In a `_skipped.face`, it is `(int) badface::key`, and TetGen sets that key to the facet's
  marker, `shellmark` (`:20445, 20462, 21337`). So it is the `.poly` facet marker here too.
  The survey's self-intersecting cube gives rows ending 8, 9 and 12: the two triangles of the
  wall that a thirteenth facet pierces, and that facet (`crates/simpa-core/tests/mesh_poly.rs`).
- The fixture's 535 rows are all -1 only because Night Mode's `.poly` wrote no facet markers:
  its facet list header is `1086 0` (`build-clean/sim_output/tcr/model.poly`), so TetGen had none
  to copy. The same missing markers make every row of that run's `.1.face` -1.
- Upstream's GUI reads the skipped markers in debug mode only: it adds 1 and later subtracts 1
  (`projet_maillage.cpp:256, 264`), so it looks each marker up in its facet table as it is. A
  -1 finds nothing, which is why the broken hall's skipped facets could not be highlighted.

### `.neigh`: no loader. Writer `outneighbors` (`tetgen.cxx:34924-35002`)

```
<count> 4
<index> <n0> <n1> <n2> <n3>                                 count lines
```

It is written as `%ld  %d` with a literal 4 (`:34958`), then `%4d    %4d  %4d  %4d  %4d`
(`:34986`).

- `n_j` is the tetrahedron across the face **opposite corner j** of the same record in `.ele`.
  This was checked on all six tetrahedra of tutorial 1 in `tetgen_golden.rs`.
- `n_j` is -1 (`HULL`) when that face is on the hull (`:34978-34982`). Otherwise it is a
  tetrahedron number in `[first, first + count)`.
- Every neighbour relation is mutual.

## Sentinels and versions

- **Versions.** No file has a version field. The TetGen these files come from is 1.6.0
  (`tetgen.cxx:7`), built from upstream `929a5c8`.
- **Index base.** `first` is 0 or 1. The four files of one run share it.
- **Hull.** A `.neigh` entry of -1 means that face is on the hull.
- **Markers.** A `.node` marker is 0 for a free interior point. In a `.face` and in a
  `_skipped.face` alike, the marker is the facet marker (in the latter through the `badface`
  key), covered above.
- **Region.** The `.ele` attribute written with `-A` is the region number. It is 1 for tutorial
  1's single room.

## The rule the Rust reader keeps

**Whenever the Rust reader accepts a file, it holds exactly the values TetGen's loader holds.**
Where TetGen would crash, guess, or read something other than what the file says, Rust refuses
with a reason (`Invalid` or `Truncated`) instead. It never returns a different value.

This was tested against the oracle on 11,301 files (see "Verification"). The mismatches allowed
by the rule are all of one kind, "Rust refuses, oracle reads". Every such case is one of these:

| input | TetGen | Rust |
|---|---|---|
| fewer records than the count | dereferences the NULL `readnumberline` returns at end of file (`:2901-2903`), in every loader | `Truncated` |
| no header at all | reads an uninitialised buffer (`load_node`, `:219-226`) | `Truncated` |
| more records than the count | ignores the rest | `Invalid` |
| missing attribute or marker | 0 | `Invalid` |
| extra fields on a line (`-nn` columns, uv values) | ignored | `Invalid` |
| junk bytes in or between fields, e.g. `1abc`, letters, a BOM, a stray `\r` | skipped, or the field is cut short | `Invalid` |
| `010`, `0x10` as integers | 8, 16 | `Invalid` |
| `3.0` as an integer, `2.7` as a face marker | 3, 2 | `Invalid` |
| integer beyond `i32` | clamped to `LONG_MAX`/`LONG_MIN` | `Invalid` |
| real that overflows (`1e999`, `-inf`) | ±inf | `Invalid` |
| real with more than 768 significant digits | MSVC's `strtod` drops the rest, unrounded (next section) | `Invalid` |
| line longer than 2 046 bytes | split into two lines | `Invalid` |
| NUL, `Ctrl-Z` | end of string, end of file | `Invalid` |
| a line that starts with a comma | the comma is skipped, except in the `.node` header, where the count becomes 0 and every field shifts one place | `Invalid` |
| first index not 0 or 1, or indices out of sequence | first index ignored and `firstnumber` stays 0; later indices never read | `Invalid` |
| `.node`: `dim` not 3, uv flag, `rbox` in the header, negative attribute count | accepted, each with its own quirk | `Invalid` |
| `.node`: negative count | calls `new REAL[negative * 3]` (`:80`); the oracle refuses before it | `Invalid` |
| `.face`: negative count | success, no faces | `Invalid` |
| a line of commas only | skipped | `Invalid` |
| decoded records larger than `2 * len + 32 KiB` | loads | `Invalid` (see Budget) |

Where both refuse (`count <= 0` in `.ele`, a corner out of range, a missing coordinate), Rust's
kind is `Invalid`, or `Truncated` for a short file.

### MSVC's `strtod` keeps 768 significant digits

Found by the oracle diff on 2026-09-23. `1.00000000000000011102230246251565404236316680908203125`
is exactly halfway between 1 and the next double. Followed by 800 zeros and a `1`, it is above
halfway, so it must round up to `3ff0000000000001`. Rust does. The oracle (MSVC UCRT, the C
runtime TetGen is built with) returns `3ff0000000000000`.

Probing with the oracle showed:
- UCRT keeps exactly 768 significant digits. A `1` in digit 768 rounds up; in digit 769 it is
  dropped.
- Leading zeros do not count, whether they come before or after the point.

Rust therefore refuses a mantissa of more than `MAX_SIGNIFICANT_DIGITS = 768` significant
digits. TetGen writes 17.

### Reading without a `.node`

Each file is read on its own. `load_tet` and `load_face` need `numberofpoints` and `firstnumber`
from a `.node` (`load_tetmesh`, `tetgen.cxx:2462-2491`, loads the `.node` first). A standalone
read therefore uses:

- `first`: the file's own first record index. It must be 0 or 1, the rule `load_node_call`
  applies to points.
- `numberofpoints = INT_MAX - 1` (`STANDALONE_POINTS`): the largest count for which TetGen's
  `numberofpoints + firstnumber` cannot overflow. Only the lower bound bites.

`check_mesh(node, ele, face?, neigh?)` then checks one run's files against each other:
- the `.ele` and `.face` share the `.node`'s `first`, and every corner is one of the `.node`'s
  points;
- the `.neigh` has one row per tetrahedron and the same `first`;
- every neighbour relation is mutual.

### Budget

The records decode to 24 bytes per point, plus 8 per attribute and 4 per marker; 4 per corner
and 8 per attribute per tetrahedron; 12 or 16 per face; and 16 per neighbour row. The reader
reserves exactly that, after checking the count against the number of data lines present, which
it counts without allocating. It refuses a file whose records would need more than
`2 * len + 32 KiB`. Only large files whose attributes print as one or two characters can reach
that limit:
- a file laid out the way `outnodes` writes it only with 5 or more such attributes per point;
- a hand-written file with single-space separators, from about 1 attribute per point, or 4 per
  tetrahedron, once it has more than about 10 000 records.

Without attributes, the densest valid files still fit, because indices must run in sequence and
so lengthen lines:
- a `.node` of `i 0 0 0` lines stays at most 22 KiB over `2 * len`, inside the reader's 32 KiB
  slack and the budget's 64 KiB;
- `.ele`, `.face` and `.neigh` stay under `2 * len`.

`tetgen_fuzz.rs` checks all of this with 300 000-record files.

## Failure modes

| condition | kind |
|---|---|
| file missing | `NotFound` |
| other I/O error | `Io` |
| empty file, no data line, or fewer data lines than the count | `Truncated` (offset = file length) |
| everything in the table above, and a corner or neighbour out of range | `Invalid`, with the line number |
| extension not `.node`, `.ele`, `.face` or `.neigh` | `Invalid` (from `read_file` / `dump_file`) |

The reader never panics and never reserves before the count has been checked
(`tetgen_fuzz.rs`: 3 × 10 000 proptest cases, each read as all four kinds).

## Canonical dump

The general rules are in `README.md`. There is no version field, so the first line is
`tetgen <kind>`. Point and tetrahedron numbers are written as they are in the file (base `first`),
never rebased.

```
tetgen node
first <first>
dim <mesh_dim>
attributes <numberofpointattributes>
markers <0|1>                  pointmarkerlist present
points <n>
<x> <y> <z> [<attr>...] [<marker>]          f64 hex ×3, f64 hex per attribute, decimal marker

tetgen ele
first <first>
corners <4|10>
attributes <numberoftetrahedronattributes>
tets <n>
<c1> ... <c_corners> [<attr>...]            decimal corners, f64 hex attributes

tetgen face
first <first>
markers <0|1>                  trifacemarkerlist present (0 for an empty file whatever the flag)
faces <n>
<a> <b> <c> [<marker>]

tetgen neigh
first <first>
tets <n>
<n0> <n1> <n2> <n3>                         -1 = hull
```

On failure, Rust prints `error <kind>` and the oracle prints `error`.

The dumps of the tutorial 1 mesh are pinned in `tetgen_golden.rs`. For example, `.neigh`:

```
tetgen neigh
first 1
tets 6
-1 -1 5 6
5 -1 -1 3
-1 6 -1 2
6 -1 -1 -1
1 -1 -1 2
-1 4 1 3
```

## Rust API

- `Kind { Node, Ele, Face, Neigh }`, with `Kind::from_path` and `Kind::extension`.
- `TetgenFile { Node(NodeFile), Ele(EleFile), Face(FaceFile), Neigh(NeighFile) }`. The fields
  follow `tetgenio`'s. Coordinates are `f64` (`REAL`), and numbers are the `i32` values as written.
- `read(kind, bytes)`. It takes a kind because the bytes cannot say which kind they are. Also
  `read_node`, `read_ele`, `read_face` and `read_neigh`.
- `read_file(path)` and `dump_file(path)`, which take the kind from the extension, and
  `dump(&TetgenFile)`.
- `check_mesh`.
- Constants: `HULL`, `MAX_LINE`, `MAX_SIGNIFICANT_DIGITS`, `STANDALONE_POINTS`.
- No writer: these files are TetGen's output.

## The oracle

`oracle/dump_tetgen.cpp` compiles `tetgen.cxx` and `predicates.cxx` with `TETLIBRARY`, so
`terminatetetgen` throws instead of exiting (`tetgen.h:2487-2490`). The oracle catches the throw
and prints `error`.

- **`.node`, `.ele`, `.face`** call `load_node`, `load_tet` and `load_face` unchanged. For `.ele`
  and `.face`, the oracle presets the context a `.node` would give, as described under "Reading
  without a `.node`".
- **`.neigh`** has no loader. The oracle follows `load_tet`'s control flow on TetGen's own
  `readnumberline`, `findnextnumber` and `strtol`, checking the neighbour rule above. This leg
  checks the Rust tokenizer against TetGen's, not a second reading of the layout.
- **Guards** cover inputs upstream does not survive: fewer number lines than the count (NULL
  dereference), no header (an unfilled buffer), and a negative `.node` count (`new[]` of a negative
  size). They count lines with `readnumberline`
  itself, so they see the file exactly as the loaders do.
- **Output.** TetGen's `printf` progress messages go to `NUL` while a loader runs, so they don't
  mix into the dump.

## Upstream GUI readers (reference only)

`Objet3D_maillage.cpp` reads the same files with `wxStringTokenizer`. It is not the reference,
and it has bugs:

- `LoadEleFile` writes `idVolume` at `idTetra - 1` **before** checking `idTetra` is in range
  (`:165` before `:166`). It also needs at least 6 tokens (`:155`), so an `.ele` written without
  `-A` fails to load.
- `LoadNodeFile` converts coordinates to `float` (`:94-96`). The `.mbin` the GUI builds from
  them keeps only single precision.
- `LoadFaceFile` refuses a header whose second number is not 1 (`:351`). It indexes
  `vertex_list[sommets.a]` without a bounds check (`:370`).
- `LoadFaceListe` reverses the winding (`:243`).
- `LoadNeighFile`'s `idTetra >= 0` is always true for an `unsigned` (`:440`).

## Verification (2026-09-23)

- **`tetgen_golden.rs`, 10 tests.** Tutorial 1's four files are read and checked for
  consistency:
  - counts 8/6/12/6;
  - every `.ele` and `.face` corner is in 1..=8;
  - `.neigh` holds -1 or 1..=6, and its 12 hull entries equal the 12 hull triangles;
  - neighbours are mutual, and each lies opposite its corner;
  - `check_mesh` passes;
  - the four dumps are pinned.

  The skipped pair reads as 535 facets with marker -1, over 1 067 points. The negative cases are
  listed in "The rule" above. The oracle cross-check builds the tetgen oracle when it is missing
  or stale, and fails when it cannot.
- **`tetgen_fuzz.rs`, 6 tests.** Three proptests of 10 000 cases each, every case read as all
  four kinds: arbitrary bytes, TetGen-alphabet text, and mutated fixtures. None panicked, and no
  case's peak allocation exceeded `budget(len)`. Three deterministic budget tests: the densest
  valid files of 300 000 records, an attribute-heavy `.node` refused within budget, and headers
  with a count of `INT_MAX` refused as `Truncated` in under 4 KiB.
- **Oracle diff** (throwaway harness, not committed). Over 11,301 files:
  - the 6 fixtures, 6 000 mutated fixtures, 4 000 generated files of every kind in varied valid
    layouts (1 282 of them then mutated once), and 1 295 `.node` files holding 1 253 hard
    decimal strings;
  - 4 657 read by both with identical dumps, 3 305 refused by both, and 3 339 refused by Rust
    and read by the oracle;
  - 0 files where the oracle refuses and Rust reads;
  - 0 files where both read and the dumps differ;
  - all 6 fixtures identical.

  Every "Rust refuses, oracle reads" case, sorted by the Rust error's category, falls under a row
  of the table above. In particular,
  all 443 refusals among 2 718 generated valid-layout files are values that overflow to
  infinity, confirmed by the oracle's own `±inf` output.
